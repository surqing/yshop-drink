# R4 批量可售库存调整

## 范围

本能力只对一个已授权门店内的现有商品 SKU 调整 **AVAILABLE 可售库存**。它不改变预占数量、销量、价格、已创建订单快照、优惠券、积分或资金数据；预占和取消释放仍由订单模块负责。它不是原料库存、实物盘点、批量调价或跨门店操作。

每批包含 1–100 个唯一的 `(productId, skuId)`。同一商品可包含多个 SKU。数量字段必须是 JSON 整数：`expectedStock` 为 0–1,000,000，`delta` 非 0 且绝对值不超过 1,000,000；调整后 SKU 可售量仍须在该范围内，商品汇总库存不得超过数据库字段上限。整批只有一个 trim 后 1–200 字的原因。门店、商品、SKU 错配、重复 SKU、空批及超限批次整批拒绝。

## API

统一部署前缀由应用配置提供；以下路径相对 `/admin-api`。全部接口要求 `shop:store-product:update`，并在服务端复用 `StoreAccessService` 重新校验当前操作者和门店/商品归属。

| 方法与路径 | 语义 |
|---|---|
| `POST /product/catalog/stock-batches/preview` | 只读预览。返回每行当前库存、期望库存、delta、预计结果和冲突代码；不写批次或操作审计。 |
| `POST /product/catalog/stock-batches` | 对整批执行原子调整。请求带 `key`；成功返回 `APPLIED`、批次 ID、实际 before/delta/after、原因和提交时间。 |
| `GET /product/catalog/stock-batches/result?key=…` | 只读查询原 key；返回 `CONFIRMED` 和原批次，或 `UNCONFIRMED`。未找到不代表原提交一定未执行。 |

请求只接受 `shopId`、`lines`、`reason` 和写请求的 `key`，不接受客户端 actor、tenant、状态或审计字段。越权混入整批拒绝，不返回部分授权资源信息。已授权资源上的库存变化使用稳定代码 `STOCK_CHANGED_REFRESH_REQUIRED` 等呈现。

## 事务和幂等

批次头存放于 `yshop_product_stock_batch`；逐行证据复用 `yshop_product_operation`，不建立第二套库存余额。执行顺序为：校验当前门店权限并锁门店；按 ID 升序锁商品；在任何业务写入前验证整批 SKU 归属和初始边界；插入并锁定幂等头；按规范化行序锁住 SKU 后重新读取并比较 `expectedStock`；增量更新 SKU 与商品汇总；插入每行审计；最后把批次置为 `APPLIED`。所有改动和回执在一个数据库事务中提交，任何冲突或写入失败全部回滚。

库存只用 `stock = stock + delta` 增量修改，不覆盖 `sales` 或 reservation。SKU 和商品行锁与订单预占/取消、商品维护按门店 → 商品 ID → SKU ID 的顺序协调。提交前的无写入预检用于确保完整资源归属已验证；提交时的加锁复读才是最终库存判断。幂等头位于商品锁之后、SKU 锁之前；相同门店请求先由门店锁串行化，冲突请求在写库存前回滚。

规范化请求摘要包含版本、门店、trim 后原因和按 `(productId, skuId)` 排序的所有 `expectedStock`/`delta`。同一操作者和 key 的同一请求返回原批次；改动门店、任一行或原因都拒绝。并发相同 key 只应用一次。不同 key 竞争同一 expected 值时，最多一个成功，失败批次不留下库存或审计变化。

## 审计与迁移

迁移文件为 `yshop-drink-boot3/sql/migrations/2026-10-25-product-stock-batch.sql`，应在既有多门店和商品目录迁移之后运行。它只增加可空的 `delta_value`、`batch_id`、非唯一批次索引及批次头表；旧历史保留，旧行的新字段为空。脚本可重复运行，检查列、索引、字符集/排序规则、字段定义和 InnoDB 引擎；遇到同名但结构不兼容的对象明确失败。

商品经营历史接口返回 `delta_value` 与 `batch_id`，可关联整批和逐行 before/after/原因。结果接口只允许原操作者并要求当前门店权限。不得根据操作记录推导或修改财务记录。

回滚时先关闭新入口并恢复应用版本，保留 additive 列、批次表、审计行和已发生的库存变化；不得直接删除批次/历史或自动反向库存调整。生产迁移、合并和部署均需另行授权。

## 管理端状态和恢复

操作入口只在明确门店并选择商品后可用；SKU 名称和库存来自服务端授权查询。页面先预览，只有输入签名仍与成功预览一致且无冲突时才允许确认。后端仍会在提交时重新校验全部状态。

提交前先将原 key 与原请求保存到当前账号/门店作用域的短期 `sessionStorage`。确定的业务拒绝不会显示成功，且要求刷新/修改后重新预览；HTTP/网络结果不确定时保留原 key 和原请求，只允许查询或显式重试原请求。重开时先查询原 key；切店、关闭窗口或切换账号时，以上下文序号丢弃迟到响应，不能污染新上下文。退出登录清除本功能的暂存项；浏览器存储不可读/写时暂停提交，避免发出无法恢复的请求。

## 验证范围

服务层覆盖整批原子性、第二行库存冲突、审计失败回滚、幂等重放/并发、授权撤销、100 个 SKU、预占/取消交互、历史快照和严格 JSON 整数反序列化。真实 MySQL 8/InnoDB 迁移验收使用随机命名、自动清理的隔离 schema。页面组件和目标 E2 场景分别验证切店竞态、HTTP 200 业务错误、响应丢失恢复、历史批次展示及库存/财务 SQL 不变量。验收结果、源码身份和环境边界记录在 R4 实施与验收报告中。
