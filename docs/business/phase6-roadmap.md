# Phase 6B–6E 业务路线图

前提：单商家多门店，共享会员。Phase 6A 建立订单正确性基线，不代表所有经营功能可直接投产。支付继续冻结，后续阶段也不得自动启用真实资金动作。

| 阶段 | 已有实现和复用价值 | 主要缺陷/缺口 | 优先级/复杂度 | 建议验收标准 |
|---|---|---|---|---|
| 6B 商品经营 | ProductCategory 两级分类，StoreProduct、Attr/AttrValue、SKU 价格/库存、Vue 商品表单、UniApp 规格弹层可以复用。6A 提供归属和库存安全边界。 | 分类/商品后台仍偏 CRUD；冷热、甜度、冰量、加料需要明确组合/加价模型。商品按店独立记录，尚无共享商品模板及差异价管理。缺版本化 SKU、批量操作审计与库存调整流水；有未付预占时目前禁止破坏性编辑。 | P0，较高 | 两店不同售价/可售规格互不污染；规格组合与加料金额由服务端计算；批量上下架有授权；库存调整和未付预占并发不覆盖库存；历史订单快照不变；售罄与跨店攻击测试通过。 |
| 6C 优惠券营销 | Coupon/CouponUser、基本发放/列表、门店 CSV 和有效期/满减字段存在；6A 支持新订单预占、支付后派生核销、取消返还及并发抢券使用保护。 | 新人资格、限领次数、兑换/领取并发、模板修改后的快照、跨店配置、到期/预占生命周期、历史券占用对账仍需专项审计。不能把 status=1 全部当已核销或全部返还。 | P1，高 | 新人券与满减券资格服务端验证；店券/全店券明确；领取/核销并发幂等；到期不误返可用；支付/取消竞争一致；历史占用有只读报告和人工迁移方案。 |
| 6D 会员运营 | 现有微信登录、MemberUser、地址、会员查询/编辑、UserBill 业务消费流水可复用；钱包只能复用已有 WalletService/不可变账本，不另建 balance。 | 等级/积分可配置规则、跨店积分归属、积分核销幂等和消费统计证据不完整。已有积分字段/接口并不证明交易一致性；先审计所有增减入口。 | P1，高 | 共享身份跨店一致；积分计提/撤销与合成支付或订单履约事件幂等，明确统一积分默认与可配置例外；禁止普通会员编辑改余额/积分；账户隐私与统计授权验证；历史资金/积分不擅自回填。 |
| 6E 门店运营 | 既有 Vue 工作台、订单状态/记录、自取编号、发货/确认收货、门店营业时间和管理员绑定可复用；6A 提供资源级门店授权、多店店长与明确总部角色。 | 接单/制作/叫号/取餐需明确状态机与并发 CAS；门店统计仍不能使用全局 Redis 值；打印商业 TODO 不等于可用打印；需要员工细粒度角色、暂停接单、设备失败重试和操作审计。 | P1，较高 | 店员不能跨店操作，店长限授权店，总部可汇总；接单→制作→叫号→取餐状态转换审计/幂等；只对合成已付订单验收；暂停与营业时间规则一致；统计可对账；打印失败可重试且不重复扣库存/资金。 |

建议先 6B 再 6C；6D/6E 分别在事件与权限契约稳定后推进。阶段估计是相对复杂度，不以未核对的类数量承诺工期。每阶段均需隔离 MySQL 并发验收、小程序真实页面 smoke、后台类型/构建及既有支付安全回归，独立 PR 审查后推进。

业务选项暂定：会员全商家共享；积分推荐商家统一但须在 6D 明确规则和可配置门店例外；优惠券默认按模板明确通用/门店范围，不根据会员所属店猜测；店长可被授予多个店，普通店员也只能操作明确分配的店，菜单权限仍控制具体操作。此处是规划，未新增营销、积分或完整运营实现。
